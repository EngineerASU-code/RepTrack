# RepTrack — рабочие инструкции

## Проект

- Основное офлайн-приложение — `android/`; сверяй команды и требования с `android/README.md`.
- Необязательный Telegram relay Stage 3 находится в `telegram-bot/` и использует Cloudflare Worker + D1. Реальное развёртывание и внешние интеграции не запускай без отдельного запроса.
- `web/` — отдельный браузерный прототип; `dist/index.html` — его копия для статического хостинга, не часть Android-сборки.
- Для поиска связей начни с `docs/project/ARCHITECTURE_INDEX.md` и текущего Graphify. Сверяй `commitSha` с `HEAD`; гипотезы подтверждай исходниками при устаревшем или неполном графе.
- ТЗ задач сохраняются в `docs/tasks/`; используй `docs/tasks/TEMPLATE.md`, не подменяй его выдуманными требованиями.

## Проверки

- Для Android нужны JDK 17/21, Android SDK API 36 и Build Tools 36.0.0. Из `android/` запускай `.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug`, `.\gradlew.bat :app:lintDebug` (Android Gradle Plugin) или с подключённым эмулятором/устройством `.\gradlew.bat :app:connectedDebugAndroidTest`.
- Для Telegram из `telegram-bot/` доступны `node --check src/index.mjs` и `node --test test/index.test.mjs`; используются встроенные возможности Node.js 24+.
- Отдельный форматтер и дополнительные линтеры не настроены; `git diff --check` проверяет пробелы в diff. CI workflow в репозитории отсутствует.
- Не запускай служебные скрипты из `tools/` или `tasks/` как тесты: они могут менять настройки, запускать процессы или обращаться к внешним API.

## Данные и рабочее дерево

- Не добавляй в Git личные отчёты тренировок, их транскрипции или скриншоты. Debug-fixture `android/app/src/debug/assets/workout-reports.json` содержит только синтетические записи; используй её и отдельные тестовые профили для проверки импорта.
- Не читай резервные копии БД, хранилища провайдеров или профили с ключами. Не показывай секреты и не добавляй их в Git.
- Перед изменениями проверь `git status`; в рабочем дереве могут быть пользовательские локальные материалы. Добавляй в Git только явно относящиеся к задаче файлы.

## OmniRoute handoff для Codex

- Перед продолжением крупной задачи проверяй лимиты инструментом `mcp__codex_app__get_usage_limits`. Поле `usedPercent` — уже израсходованная доля; остаток вычисляется как `100 - usedPercent`.
- Для многошаговой активной задачи заранее создай и обновляй handoff-файл в `tasks/`, проверь `node tools/omniroute-fallback/watch-quota.mjs --status` и переиспользуй уже активный watcher вместо запуска второго. Если его нет — запусти `node tools/omniroute-fallback/watch-quota.mjs tasks/<handoff>.md`. Watcher читает только лимиты через Codex App Server; текст задачи уходит провайдеру только после срабатывания порога.
- Если остаток любого доступного основного окна Codex (пятичасового `primary` или недельного `secondary`) стал **10% или меньше**, watcher автоматически запускает локальный worker, не дожидаясь нуля. Отсутствующее значение не считай нулём. После запуска worker-а не вноси параллельные изменения в те же файлы.
- В handoff-файле держи цель, критерии готовности, текущий прогресс и следующий шаг. Не включай ключи, конфиги провайдеров, базы данных, резервные копии или личные отчёты тренировок. Удаление task-файла отменяет ещё не сработавший watcher.
- После ответа проверь фактический diff и результаты разрешённых проверок. Worker не должен коммитить или пушить.
- Ручной запуск доступен через `$omniroute-manual-handoff` и не зависит от порога квоты.
