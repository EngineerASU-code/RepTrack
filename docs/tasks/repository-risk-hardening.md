## Исходное поведение

- В Git отслеживаются личные исходные изображения в `database/`, производный `android/app/src/debug/assets/workout-reports.json` и описывающий их `database/README.md`. README подтверждает, что JSON транскрибирован из личных исходников. Публичный доступ подтверждён владельцем, поэтому исходники и производные личные данные нельзя оставлять в публичной истории.
- CI workflow в репозитории не обнаружен. Отдельный форматтер и дополнительный статический анализ не настроены. Доступны Android Gradle проверки, включая встроенный `lintDebug`, и локальные проверки Telegram через `node --check` и `node --test`.
- `telegram-bot/test/index.test.mjs` использует заглушки. `telegram-bot/README.md` указывает, что тесты не проверяют живые Bot API, D1 или развёрнутый Worker. В `src/index.mjs` Worker обновляет статус отправки после вызова `sendDocument`; при принятии файла Telegram и сбое до записи статуса повтор может отправить его снова. У Bot API нет ключа идемпотентности для `sendDocument`.
- В `docs/project/ARCHITECTURE_INDEX.md` уже перечислены Android instrumented tests и прямо отмечено, что граф Graphify не связал `MainActivity.kt` с ними. Например, в проекте существуют `WorkoutImeAcceptanceTest.kt`, `VisualAcceptanceTest.kt` и `AccessibilityAdaptiveTest.kt`; пустая связь графа не означает отсутствие UI-тестов.
- Контекст проверки: `main`, `HEAD` `648404812444da2eaa87e7608f94eff1856396bd` на момент подготовки ТЗ.
- Решения владельца от 2026-11-17: репозиторий должен быть публичным; переписывание Git-истории и force push разрешены, если подтверждены личные данные и перед операцией согласован план очистки.
- Решения владельца по качеству и доставке: использовать KtLint для Kotlin и Prettier для JavaScript/web; подготовить отдельного Telegram-бота через BotFather и staging Worker/D1; при неоднозначном результате Telegram повторять доставку, принимая риск копии.

Локально `main` и `origin/main` указывают на `648404812444da2eaa87e7608f94eff1856396bd`; GitHub сообщает только ветку `main`; локальных тегов нет. ## Требования

1. Установить и записать классификацию каждого отслеживаемого исходного отчёта и debug fixture без помещения личного содержимого в отчёты проверок. Если fixture содержит личные данные, заменить его синтетическим набором, пригодным для воспроизводимых тестов.
2. Обеспечить публичный доступ к репозиторию, как решил владелец. Удалить личные исходные снимки, производную транскрипцию и детали импорта из публичного содержимого; заменить нужные для демонстрации/тестов данные синтетическими. Перед исторической очисткой подготовить перечень затрагиваемых refs и план переписывания. Владелец разрешил необходимое переписывание истории и force push после согласования плана.
3. Настроить CI для pull request и обновлений основной ветки. Проверки должны покрывать Telegram-синтаксис и unit tests, Android unit tests, сборку debug и встроенный Android lint. Секреты и production-сервисы для обычного CI не требуются.
4. Настроить KtLint для Kotlin и Prettier для JavaScript/web. CI должен проверять форматирование и Android lint, а начальное применение не должно включать несвязанные массовые изменения.
5. Подготовить повторяемую интеграционную проверку Telegram relay на отдельном тестовом боте, создаваемом через BotFather, и staging Worker/D1. Она должна покрывать регистрацию маршрута, приём и пересылку документов, сохранение статусов, повтор webhook и восстановление после сбоя. До появления тестового токена и staging-ресурсов интеграционные сценарии не запускаются; production данные и секреты не используются.
6. Использовать повторную доставку (at-least-once) при retry, принимая риск копии, описанный владельцем. Не заявлять гарантию exactly-once. Состояния PDF и зашифрованного файла, повтор webhook и восстановление должны соответствовать этой семантике и иметь проверяемые сценарии сбоев.
7. Связать `MainActivity.kt` и основные пользовательские потоки с конкретными instrumented tests так, чтобы разработчик мог проверить покрытие по исходникам и документации. Если Graphify не позволяет исправить прямые связи, архитектурный индекс должен сохранять явную карту тестов и объяснять ограничение графа.

## Ограничения

- Реальные Bot API, Cloudflare Worker и D1 проверяются только на ресурсах, созданных специально для тестирования; production-развёртывание не является частью этой задачи.
- Telegram Bot API не предоставляет идемпотентный ключ для `sendDocument`; без подтверждённого механизма дедупликации нельзя обещать exactly-once доставку.
- Содержимое личных изображений и JSON не включать в логи, CI-артефакты, фикстуры отчётов или публичную документацию.
- Удаление файлов из текущей ветки не удаляет их из предыдущих коммитов. Владелец разрешил очистку истории и необходимый force push только при подтверждении личных данных в истории и после согласования плана очистки.
- Требования Android по JDK 17/21 и Android SDK API 36 / Build Tools 36.0.0 остаются в силе.
