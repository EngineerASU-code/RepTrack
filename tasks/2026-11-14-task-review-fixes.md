Исходная база ревью: `HEAD d16bcfc`, незакоммиченные изменения и новые файлы. Рабочее дерево содержит предшествующую реализацию Stage 2 и Stage 3: сохранять её, не сбрасывать и не перезаписывать чужие правки. Строки ниже — ориентиры на дату ревью; при реализации найти актуальные определения.

Работать в `android/` и `telegram-bot/`; учитывать `AGENTS.md`. Ссылки корневого `AGENTS.md` на отсутствующий GASS Configurator к RepTrack неприменимы. Применять Ponytail: минимальные изменения в общих точках поведения, стандартные средства платформы, без нового app-сервера и лишних зависимостей. Не создавать коммиты, не публиковать и не развёртывать Worker, не отправлять сообщения реальным пользователям. Не читать и не запрашивать реальные токены в чате.

## R1. Отправка индивидуальной программы подопечного — MAJOR

Места: `DiaryRepository.createProgramPackage`, `SettingsScreen`, `selectedProgramLink`, `DiarySnapshot.trainerPlans`.

Проблема: отправка предлагает только личные шаблоны тренера. Назначенная подопечному независимая копия с индивидуальными нагрузками недоступна для отправки.

Требования:

- Выбор программы для доверенной связи тренера должен включать планы именно локального профиля этой связи, в том числе индивидуально отредактированные назначения.
- При необходимости сохранить явную отправку личного шаблона как отдельный понятный выбор. Не подменять индивидуальную копию исходным шаблоном.
- Проверять владельца и адресата в repository, а не только фильтровать UI.
- Сохранять стабильный ID отправляемой программы и монотонную версию при последующих правках. Обновление той же программы на устройстве подопечного должно обновлять прежнюю локальную копию с предпросмотром; не создавать новую программу при каждом экспорте.

Приёмка:

1. Назначить один шаблон двум профилям A и B; изменить вес/повторы только у A.
2. Передать A его программу; расшифрованный пакет содержит изменения A. B и личный шаблон остаются прежними.
3. Попытка отправить программу B через связь A отклоняется.
4. Изменить программу A и передать снова: получатель видит обновление прежней программы с новой версией. Активная сессия и завершённая история не переписываются.

## R2. Сохранность принятого отложенного обновления в backup — MAJOR

Места: `createEncryptedBackup`, `encodeDiaryArchive` / `decodeDiaryArchive`, `restoreDiary`, `incoming_programs`, `applyAcceptedIncomingPrograms`.

Проблема: принятое во время активной тренировки обновление хранится в `incoming_programs`, отсутствует в backup и теряется при восстановлении.

Требования:

- Включить в парольную резервную копию содержимое принятого отложенного обновления и необходимые несекретные метаданные его локального применения.
- Восстановление на новой установке не должно требовать старого Keystore или восстанавливать отозванное доверие. Секреты связей по-прежнему не переносить; определить безопасное локальное применение уже принятого обновления отдельно от будущего обмена.
- Сохранить чтение прежних версий backup и транзакционность восстановления. Новый формат версионировать; менять схему БД только при необходимости, с миграцией без удаления пользовательских данных.
- Повреждённое или несовместимое обновление отклонять до замены данных либо откатывать восстановление целиком. Не превращать повреждённую программу в частично применённую.

Приёмка:

1. На связанном подопечном начать тренировку и принять входящую новую версию программы; она ожидает окончания.
2. Создать backup, восстановить на независимой установке с паролем, без старых ключей.
3. Активная тренировка восстанавливается неизменной. После завершения/отмены уже принятое обновление применяется один раз; доверенная связь автоматически не восстанавливается.
4. Повторный запуск не применяет обновление повторно. Старые backup продолжают читаться; ошибочный импорт сохраняет прежние данные.

## R3. Потеря webhook при зависшем PROCESSING — MAJOR

Места: `telegram-bot/src/index.mjs`, `fetch`, `claimUpdate`, `finishUpdate`.

Проблема: повтор update в пределах lease получает HTTP 200 без обработки. Если прежний запуск аварийно завершился, Telegram считает update принятым, а механизма подхвата нет.

Требования:

- Различать завершённый update и незавершённый занятый update. Успешно подтверждать только завершённую работу либо надёжно поставленную в очередь работу.
- Для занятого незавершённого update сохранить возможность Telegram retry; после истечения lease разрешать восстановление обработки.
- Захват/перехват lease должен быть атомарным, без одновременного исполнения одного update двумя обработчиками.
- Учитывать существующие стадии пересылки PDF и пакета. Не обещать exactly-once для Bot API: документировать оставшееся окно дубликата между внешней отправкой и записью статуса.
- Сохранить проверку webhook secret, квоты и отсутствие файлов в D1. Не добавлять платную инфраструктуру ради исправления.

Приёмка локальными тестами без сети:

1. Новый update выполняется и получает успешный ответ после завершения.
2. Повтор завершённого update не повторяет обработку.
3. Повтор с живым PROCESSING не подтверждается как завершённый; внешние вызовы не повторяются параллельно.
4. Истёкший lease подхватывается; два конкурирующих запроса не получают lease одновременно.
5. Ошибка обработки сохраняет retry; повтор после PDF_SENT продолжает пакет, не начинает PDF заново.

## R4. Повторная отправка PDF завершённой тренировки — MAJOR

Места: завершение тренировки в `MainActivity`, `HistoryScreen`, экспорт в настройках, `createTelegramDelivery`.

Проблема: после завершения и отмены Sharesheet или ошибки подготовки нет UI для повторного создания `.rptdelivery`; имеющийся экспорт истории создаёт только `.rptresult`, который бот не обрабатывает.

Требования:

- Из истории личного профиля можно выбрать завершённую тренировку и повторно подготовить/отправить `.rptdelivery` доверенному тренеру.
- Использовать общие генерацию PDF, шифрование и Android Sharesheet; повторная отправка не меняет тренировку и не завершает её второй раз.
- Перед каждой передачей читаемого PDF явно показывать, что он доступен Telegram/боту. Доставку и импорт не считать подтверждёнными по открытию Sharesheet.
- Предпочесть повторное использование подготовленного пакета, если он сохранился и ещё действителен; допустимо создать новый валидный пакет при утрате кэша, сохранив ID события тренировки для дедупликации импорта.
- Ошибка генерации или отсутствие связи должны быть понятны пользователю; история сохраняется.

Приёмка:

1. Завершить тренировку с отправкой, отменить Sharesheet, открыть историю и отправить PDF/пакет снова.
2. После перезапуска приложения повторная подготовка доступна без активной тренировки.
3. Повторный импорт не создаёт вторую тренировку; неверный профиль/отозванная связь не допускаются.
4. Отмена, ошибка подготовки и смена получателя не изменяют сохранённые результаты.

## R5. Предпросмотр порядка и повторяющихся упражнений — MINOR

Место: `DiaryRepository.planChanges`; учитывать существующий `planDiffSummary`, чтобы не создавать два расходящихся правила сравнения.

Требования:

- Перестановка упражнений должна явно отражаться в различиях.
- Повторяющиеся названия не должны схлопываться и скрывать добавление, удаление или изменение отдельного вхождения.
- Сравнение учитывать, что локальные ID после импорта отличаются от ID источника. Не сообщать о полной замене только из-за новых локальных ID.
- Сохранять разумное ограничение длины списка с указанием оставшихся изменений.

Приёмка: перестановка A/B, два одинаково названных упражнения с разными параметрами, удаление одного повторения и неизменённый план дают корректный предпросмотр. Только фактически неизменённый план показывает отсутствие изменений.
